# 킹덤 라이즈 목표 제품 스펙

- 문서 상태: 제품·디자인·엔지니어링·QA의 승인 기준
- 대상 패키지: `packages/kingshot`
- 제품명: **킹덤 라이즈 / Kingdom Rise** (`kingshot`은 배포 슬러그일 뿐 게임 브랜드가 아님)
- 기준 저장 형식: **v7**

## 1. 문서의 권위와 규범

1. 이 문서는 현재 구현을 설명하는 문서가 아니라 팀이 만들어야 할 **목표 제품의 단일 권위 사양**이다.
2. 이 문서와 README, 코드, 테스트, 과거 동작이 충돌하면 제품 동작에는 이 문서를 우선 적용한다. 수치 변경은 이 문서를 먼저 개정하고 config와 테스트를 함께 맞춰야 한다.
3. **MUST/해야 한다**는 출시 차단 요구, **MUST NOT/해서는 안 된다**는 금지, **SHOULD/권장한다**는 합리적 예외에 근거와 회귀 테스트가 필요한 요구, **MAY/할 수 있다**는 선택 사항이다.
4. 구현 현황과 갭 절은 진단 정보이며 목표 계약을 약화하지 않는다. 미구현 MUST는 삭제할 요구가 아니라 해결할 갭이다.
5. 모든 경제·전투·저장 수치는 중앙 config와 Phaser 비의존 순수 시스템에 단일 정의되어야 하며 UI, 저장 정산, 테스트가 같은 정의를 사용해야 한다.

## 2. 제품 정의

### 2.1 비전과 타깃

- 킹덤 라이즈는 오리지널 중세 세계의 **싱글플레이 2D 픽셀아트 전략/방치형 브라우저 게임**이어야 한다.
- 플레이어는 작은 정착지의 군주로서 생산을 안정화하고 화롯불을 유지하며 건설·훈련·연구·영웅·방어를 조합해 20회의 침략을 원하는 시점에 격퇴해야 한다.
- 1차 타깃은 한국어 사용자, 짧게 여러 번 접속하는 캐주얼 전략 사용자, 조합과 수치의 예측 가능성을 선호하는 사용자다. 영어 사용자는 동등한 기능을 받아야 한다.
- 플랫폼은 최신 데스크톱·모바일 Chromium, Safari, Firefox 계열 브라우저다. 설치, 로그인, 네트워크 연결 없이 로컬 플레이가 가능해야 한다.
- 첫 의미 있는 행동까지 1분 이내, 일반 접속 세션은 3~15분, 캠페인은 여러 세션에 걸친 누적 진행을 목표로 한다. 방치 복귀는 최대 8시간을 의미 있게 정산해야 한다.

### 2.2 제품 원칙

1. **선택한 때에 싸운다.** 침략은 시간으로 자동 시작되지 않는다. 플레이어가 Town에서 `B` 또는 전투 버튼을 눌러야만 방어전이 시작되어야 한다.
2. **결과를 설명할 수 있다.** 동일 저장 상태와 웨이브는 항상 같은 결과를 내야 하며 상성, 연구, 영웅, 방어, 사상자, 보상/약탈의 원인을 화면에서 확인할 수 있어야 한다.
3. **방치는 진행을 돕되 플레이를 대체하지 않는다.** 생산·타이머는 오프라인에도 진행하지만 전투, 구매, 퀘스트 수령은 자동 수행하지 않는다.
4. **화롯불은 핵심 경제다.** Hearth/Warmth는 장식이나 선택 모드가 아니라 목재 수요와 생산 효율을 연결하는 상시 핵심 시스템이어야 한다.
5. **실패는 회복 가능하다.** 패배해도 마을·건물·연구·영웅·캠페인 최고 진행은 사라지지 않으며 다시 생산하고 훈련해 같은 웨이브에 도전할 수 있어야 한다.
6. **한눈에 읽힌다.** 현재 자원, 실제 순생산, 온기, 전투 준비도, 진행 목표, 저장 상태를 모바일에서도 추론할 수 있어야 한다.
7. **범위보다 완성도다.** 20웨이브 이후 무한 성장, 온라인 기능, 과금보다 접근성·저장 안전성·일관된 피드백을 우선한다.

### 2.3 비목표

- 본 제품은 실시간 전략 조작, 도시 배치 샌드박스, 서사형 RPG, 경쟁 랭킹, 장기 무한 캠페인을 목표로 하지 않는다.
- 전투 중 개별 유닛 명령, 진형 편집, 확률 치명타, 가챠, 절차 생성 웨이브는 제공하지 않는다.
- 제3자 게임의 이름·캐릭터·세력·스토리·아트·오디오를 사용해서는 안 된다. 모든 출하 에셋은 프로젝트 원본이거나 명확히 허가되고 출처가 기록되어야 한다.

## 3. 사용자 여정과 화면 상태

### 3.1 필수 플로우

1. **Boot/Preload → Title**: 폰트와 필수 에셋을 준비하고 실패 가능한 항목은 안전한 대체물로 처리한 뒤 타이틀을 표시한다.
2. **Title → Town**: 저장이 없으면 `새 왕국/Play`, 있으면 `이어하기/Continue`를 기본 행동으로 제공한다. 새 왕국은 확인 없이 기존 저장을 덮어써서는 안 된다. 설정과 한·영 전환을 제공한다.
3. **Town → 패널 → Town**: 건물 클릭 또는 하단 버튼으로 업그레이드, 훈련, 연구, 영웅, 퀘스트, 설정 중 하나의 패널만 연다. `Esc`, 닫기, 바깥 영역 탭으로 안전하게 닫고 상태를 잃지 않는다.
4. **Town → Battle**: 병력이 1명 이상이고 캠페인이 미완료일 때 `B`/전투 버튼은 다음 미완료 웨이브에 현재 상비군 전부를 수동 출정시킨다. 진입 직전에 저장해야 한다.
5. **Battle 진입과 원자 커밋**: 전투는 진입 시 군대·웨이브·연구·영웅·방어를 snapshot해 순수 공식으로 한 번 확정한다. 연출을 예약하기 전에 사상자·생존자·보상 또는 약탈·`waveCleared`·`battlesWon`을 메모리 상태에 적용하고, 변경된 전체 snapshot을 한 번 저장해야 한다. 저장 성공 후에만 전투 연출을 시작한다. 저장 실패 시 원래 snapshot으로 rollback하고 전투를 시작하지 않으며 재시도를 제공한다. skip/speed는 이미 커밋된 결과를 재생할 뿐 상태를 다시 적용하지 않는다.
6. **Battle/GameOver 복구**: 선택적 `lastBattleReceipt`는 `{wave, win, reward, penalty, casualties, survivors, committedAt}`를 보관해 reload 후 결과 요약을 한 번 재표시할 수 있다. receipt 유무와 무관하게 경제 상태는 이미 커밋되어야 하므로 애니메이션 중 reload·close로 손실을 회피하거나 보상을 중복 수령할 수 없어야 한다. GameOver는 커밋된 결과만 표시하고 Town 복귀가 항상 가능해야 한다. 캠페인 미완료 시 생존 병력이 있으면 다음/동일 웨이브 출정을 명시적으로 선택할 수 있다.
7. **캠페인 완료 → Town/재전투**: 웨이브 20 첫 승리 후 Town에서 자유 건설·생산·훈련·연구·영웅 관리를 계속할 수 있다. 전투는 이미 완료한 1~20 웨이브의 리플레이만 허용한다.

### 3.2 첫 실행과 복귀

- 첫 실행 튜토리얼은 환영, 청사 선택, 청사 Lv.2, 자원·온기, 제재소, 병영·첫 훈련, 전투·퀘스트의 7단계를 안내해야 한다.
- 튜토리얼은 언제든 건너뛸 수 있고 완료/건너뛰기 상태를 즉시 저장해야 한다. 이전 버전 사용자를 첫 실행 튜토리얼로 되돌려서는 안 된다.
- 복귀 시 1초 이상이고 총 획득량이 1 이상인 오프라인 정산은 경과 시간, 자원별 순획득, 온기 영향, 완료된 건설·연구·훈련을 요약해야 한다.

## 4. 경제와 건설 계약

### 4.1 자원, tick, 저장 상한

- 자원은 **식량(food), 목재(wood), 석재(stone), 금화(gold)** 네 종류만 핵심 통화로 사용한다. 표시 순서도 이 순서를 따른다.
- 새 왕국의 시작 보유량은 `식량 300 / 목재 400 / 석재 250 / 금화 50`이어야 한다.
- 권위적 시뮬레이션 tick은 **1,000ms**다. 라이브 프레임 delta는 누적해 동일한 경과 시간을 1초 단위 결과와 수치적으로 같게 처리하고, 탭 정지 후 한 프레임에 과도한 중복 생산을 내지 않아야 한다.
- 기본 수동 생산 저장 상한은 자원별 **5,000**이며 `실제 상한 = 5,000 × 연구 저장 배율`이다.
- 상한은 건물의 라이브·오프라인 **수동 생산**에만 적용한다. 전투·퀘스트 보상은 상한을 초과할 수 있고 지출은 보유량을 0 아래로 내릴 수 없다.
- 복수 자원 비용은 원자적으로 검증·지출해야 한다. 하나라도 부족하면 아무 자원도 차감하지 않고 부족 항목을 표시한다.

### 4.2 건물과 청사 게이트

| 건물 | 기본 비용(Lv.0→1) | 기본 기능 | 필요 청사 |
|---|---:|---|---:|
| 중앙 청사 | 목재 100, 석재 60 | 다른 건물 레벨 상한, 최대 온기/연료 효율 | 0 |
| 농장 | 목재 40, 식량 20 | 식량 2.0/s | 1 |
| 제재소 | 식량 40, 석재 20 | 목재 1.6/s | 1 |
| 채석장 | 목재 80, 식량 40 | 석재 1.0/s | 2 |
| 광산 | 목재 120, 석재 80 | 금화 0.5/s | 3 |
| 병영 | 목재 120, 석재 80 | 훈련 큐 | 2 |
| 연구소 | 목재 160, 석재 120, 금화 60 | 기술 트리 | 3 |
| 성벽 | 목재 90, 석재 140 | 레벨당 방어 40 | 2 |
| 감시탑 | 목재 120, 석재 100, 금화 30 | 레벨당 방어 25 | 3 |

- 중앙 청사는 새 게임에서 Lv.1, 나머지는 Lv.0이어야 한다. 모든 건물 최대 레벨은 20이다.
- 건설 슬롯은 **건물 종류별 1개**다. 같은 건물은 현재 업그레이드가 끝날 때까지 다음 업그레이드를 예약할 수 없지만 서로 다른 건물은 자원과 게이트를 만족하면 동시에 건설할 수 있다. 전역 슬롯이나 별도 대기열은 두지 않는다.
- 동일 timestamp에 여러 건물이 완료되면 `(upgradeEndsAt 오름차순, 중앙 청사→농장→제재소→채석장→광산→병영→연구소→성벽→감시탑)` 순으로 하나의 원자 completion batch를 적용한다. 같은 경계의 생산 계산은 전체 batch 완료 뒤 새 레벨을 사용한다.
- 비청사 건물은 필요 청사 레벨을 만족해야 건설할 수 있고 자기 레벨이 현재 청사 레벨을 초과해서는 안 된다. 진행 중 업그레이드도 이 규칙을 위반해서는 안 된다.
- 현재 레벨을 `L`이라 할 때 각 비용 성분은 `ceil(기본 비용 × 1.6^L)`, 목표 레벨은 `L+1`, 기본 시간은 `4 × (L+1)초`다.
- 실제 시간은 `기본 시간 × 연구 buildSpeed 배율`이며 시작 시 확정한다. 비용은 시작 시 선불, 완료 전 취소·환불은 지원하지 않는다.
- 생산 건물 Lv.`L≥1`의 기초 생산은 `기본 생산 × 1.35^(L-1)`이다.
- 실제 자원별 총생산은 `기초 생산 합 × 연구 production 배율 × 활성 경제 영웅 배율 × 온기 배율`이다.
- 마을 방어력 `D = 40 × 성벽 레벨 + 25 × 감시탑 레벨`이며 전투 계약 외 다른 숨은 방어 보정은 두지 않는다.
- HUD의 `+/s`는 기초치가 아니라 Hearth 목재 소모까지 분리해 보이는 **실제 총생산과 순변화**를 표시해야 한다. 패널 시간도 연구 적용 후 실제 남은 시간을 표시해야 한다.

## 5. Hearth/Warmth 핵심 시스템

- Town은 항상 하나의 **화롯불(Hearth)**과 **온기(Warmth)**를 보유해야 한다. 별도 모드나 해금 조건으로 숨겨서는 안 된다.
- 청사 레벨 `T`에서 최대 온기 `Wmax = 100 + 20 × (T-1)`이다. 현재 온기는 `[0, Wmax]`로 제한하며 청사 업그레이드로 최대치가 늘어도 현재치를 공짜로 채우지 않는다.
- 유일한 연료는 목재다. 초당 연료량은 `0.5 × max(0.4, 1 - 0.05 × (T-1))` 목재다.
- 한 tick의 전체 연료를 낼 수 있으면 해당 양을 소비하고 온기를 초당 8 증가시킨다. 낼 수 없으면 부분 연소/부분 차감 없이 온기를 초당 5 감소시킨다. 최대 온기에서도 유지 연료는 계속 소비한다.
- 온기 비율 `r = current/Wmax`일 때 생산 배율은 `0.25 + 0.75 × clamp(r,0,1)`이다. 온기 0에서도 생산은 25% 아래로 내려가지 않고, 최대 온기에서 100%다.
- tick 순서는 **완료 타이머 반영 → tick 시작 온기로 생산 계산·상한 적용 → 새 목재를 포함해 연료 판정·온기 갱신 → HUD 갱신**으로 고정한다. 따라서 갱신된 온기는 다음 생산 tick부터 적용한다.
- HUD는 현재/최대 온기, 백분율, 생산 배율, 초당 목재 소비, 예상 연료 지속 시간을 표시해야 한다. 35% 미만은 색상만이 아닌 아이콘·텍스트·음향 선택지로 경고해야 한다.
- 오프라인 정산도 같은 1초 순서, 같은 상한, 같은 연료 전액 판정과 온기 곡선을 사용해야 하며 “오프라인에는 화롯불이 멈춘다”는 예외를 두어서는 안 된다.

## 6. 훈련, 병종, 연구, 영웅, 퀘스트

### 6.1 훈련 큐와 5병종

- 병영 건설 후에만 훈련할 수 있다. 비용은 enqueue 시 선불이며 큐는 최대 6개 batch, batch당 1~20명, 앞에서부터 순차 진행한다.
- batch 완료 시 전원이 동시에 상비군에 합류한다. 훈련 취소·순서 변경·부분 환불은 지원하지 않는다.

| 병종 | 1명 비용 | 시간 | HP/공격/공속 | 단위 원시 전투력 |
|---|---:|---:|---:|---:|
| 창병 | 식량 20, 목재 10 | 5초 | 60/10/1.0 | 25.0 |
| 궁병 | 식량 15, 목재 25 | 7초 | 40/14/1.2 | 26.8 |
| 기사 | 식량 40, 금화 20 | 12초 | 140/22/0.8 | 52.6 |
| 기병 | 식량 35, 목재 15, 금화 10 | 9초 | 90/18/1.0 | 40.5 |
| 공성 병기 | 식량 30, 목재 60, 석재 40, 금화 15 | 16초 | 200/34/0.5 | 67.0 |

- 상성 오각형은 `창병 → 기병 → 궁병 → 공성 병기 → 기사 → 창병` 순이다. 각 병종은 뒤의 두 병종에 1.5×, 자신에 1.0×, 앞의 두 병종에 0.75×다.
- 적 역할은 침략자=창병, 광전사=기사, 공성 망치=공성 병기, 기습병=기병으로 매핑한다. 상성은 HUD와 병종 도움말에서 확인 가능해야 한다.
- 연구 훈련 배율은 enqueue 시 실제 batch 시간에 반영한다. 라이브·오프라인 완료 모두 상비군과 누적 `troopsTrained`를 정확히 한 번 증가시키고 완료 피드백을 낸다.

### 6.3 영웅

- 영웅은 전쟁 역할 2명(Ser Alden, Kara Stormblade), 경제 역할 2명(Mira Goldhand, Old Bram)이어야 한다.

| 영웅/역할 | 영입 비용 | 기본/레벨당/별당 보너스 | 레벨업 기본 비용 | 승급당 조각 |
|---|---:|---:|---:|---:|
| Ser Alden/전쟁 | 금화 200, 식량 120 | 0.12/0.04/0.06 | 금화 60, 식량 40 | 10 |
| Kara Stormblade/전쟁 | 금화 320, 목재 160 | 0.15/0.05/0.07 | 금화 80, 목재 50 | 12 |
| Mira Goldhand/경제 | 금화 240, 석재 120 | 0.12/0.04/0.06 | 금화 50, 석재 40 | 10 |
| Old Bram/경제 | 식량 300, 목재 150 | 0.10/0.035/0.05 | 식량 60, 목재 40 | 8 |

- 영입 비용은 선불이고, 영웅은 Lv.1~10, 0~5성이다. 전역 활성 영웅은 동시에 한 명만 허용한다. 첫 영입 영웅은 자동 활성화하고 이후 선택은 명시적이어야 한다.
- 전쟁 영웅은 전투 공격 배율에만, 경제 영웅은 생산 배율에만 기여한다. 비활성 영웅은 배율을 제공하지 않는다.
- 영웅 배율은 `1 + baseBonus + perLevelBonus×(level-1) + perStarBonus×stars`다. 레벨업 비용은 `기본 비용 × 현재 레벨`, 승급은 영웅별 정해진 조각을 소비한다.
- 영입 전 받은 조각도 영웅별 지갑에 영구 보존해야 한다. 영입 여부 때문에 퀘스트 조각이 소멸해서는 안 된다.
- 영웅 패널의 **왕실 후원**은 반복 가능한 확정 조각 공급원이다. Alden은 금화120+식량100, Kara는 금화150+목재120, Mira는 금화120+석재100, Bram은 식량150+목재120을 원자적으로 소비해 선택 영웅 조각 1개를 즉시 지급한다. 영입 전후 모두 이용 가능하고 횟수·일일 제한·RNG·가격 상승은 없다.
- 왕실 후원 버튼은 현재 비용, 보유 자원, 조각 보유량, 다음 승급까지 부족량을 표시한다. 자원이 하나라도 부족하면 소비·조각·저장 상태를 전혀 바꾸지 않으며 성공 시 비용 차감과 조각 지급을 한 번의 즉시 저장으로 확정한다. 따라서 모든 영웅은 수동 생산만으로 5성까지 도달 가능해야 한다.

## 7. 20웨이브 수동 방어 캠페인

### 7.1 출정과 진행

- 캠페인은 정확히 20웨이브다. **주기적 자동 침략, 카운트다운 자동 진입, 오프라인 자동 전투를 구현해서는 안 된다.**
- Town의 전투 버튼과 `B`만 다음 미완료 웨이브를 시작한다. 출정 전 대상 웨이브, 아군 총원/전투력, 적 구성, 상성 경고, 마을 방어 기여를 미리 보여야 한다.
- 병력이 0이면 씬을 전환하지 않고 훈련 필요 메시지와 병영 바로가기를 제공한다. 출정은 상비군 전부를 사용하며 부분 편성은 비지원이다.
- 패배하면 `waveCleared`를 바꾸지 않고 같은 웨이브를 다시 준비한다. 승리하면 정확히 1 증가시키며 이미 완료한 웨이브가 진행을 재증가시켜서는 안 된다.

### 7.2 웨이브와 보상

- 1-based 웨이브 `n`의 적 수는 다음과 같다: 침략자 `3+floor(1.5n)`; 광전사는 `n≥3`일 때 `1+floor((n-3)/2)`; 공성 망치는 `n≥5`일 때 `1+floor((n-5)/3)`; 기습병은 `n≥7`일 때 `1+floor((n-7)/2)`.
- 첫 승리 보상은 배율 `s=1.25^(n-1)`에 대해 식량 `round(60s)`, 목재 `round(50s)`, 석재 `round(30s)`, 금화는 n=1에서 0, n≥2에서 `round(15s)`다.
- 보상은 해당 웨이브의 최초 클리어 결과를 적용할 때 정확히 한 번만 지급한다. 저장·새로고침·skip·중복 입력으로 재지급해서는 안 된다.

### 7.3 결정론적 전투 제품 계약

- 전투에는 난수, 시간 기반 변동, 프레임 의존 판정이 없어야 한다. 결과는 `(군대, wave, 완료 연구, 활성 영웅, 방어 건물)`의 순수 함수다.
- 단위 원시 전투력은 `P = attack × attackSpeed + hp × 0.25`다. 적 원시 전투력은 침략자 21.5, 광전사 45.1, 공성 망치 80.0, 기습병 38.85다.
- 웨이브 전투력 `W = Σ(enemyCount[e] × enemyPower[e])`다.
- 각 병종 `t`의 대웨이브 상성 가중치 `C_t = Σ((enemyCount[e]×enemyPower[e]/W) × counter[t,e])`다.
- 구성 전투력 `G = Σ(troopCount[t] × troopPower[t] × C_t)`다.
- 최종 아군 전투력 `E = G × 연구공격배율 × 활성전쟁영웅배율 + D`다. 전투 HUD가 표시하는 아군 전투력은 바로 이 E여야 한다.
- `E>0 && E≥W`이면 승리, 아니면 패배다. 동률은 승리로 고정한다.
- 승리 사상률 `f = min(1, W/E/연구방어배율)`다. 병종별 손실은 `floor(count×f)`이며 승리한 비어 있지 않은 stack 전체가 사라지지 않도록 최대 `count-1`로 제한한다. 압도적 승리의 0손실은 허용한다.
- 패배 방어 커버 `c = clamp(E/W,0,1)`이고 병종별 생존자는 `min(count-1, round(count×0.5×c))`, 사상자는 `count-survivors`다. 패배한 비어 있지 않은 stack은 최소 1명을 잃는다.
- 패배 약탈은 자원별 `floor(해당 웨이브 첫 승리 보상 × (1-c))`이며 실제 보유량에서 0 아래로 내려가지 않게 차감한다. E에 방어 D가 포함되므로 성벽·감시탑은 승패, 생존자, 약탈을 동시에 완화한다.
- 결과 화면은 E/W, 상성 기여, 연구·영웅 배율, D, 병종별 투입/사상/생존, 자원별 보상 또는 약탈을 보여야 한다.

### 7.4 캠페인 완료 후 상태

- 웨이브 20 최초 승리 시 `waveCleared=20`을 저장하고 캠페인 완료를 선언한다. 웨이브 21 이상을 생성·표시·저장·보상해서는 안 된다.
- 완료 후 Town의 건설·생산·Hearth·훈련·연구·영웅·퀘스트는 계속 작동한다.
- 완료 후 전투 버튼은 완료한 1~20 웨이브 선택기를 연다. 재전투는 **무상태 리플레이**로 고정한다: 현재 군대와 보너스로 동일 공식을 시연하되 병력, 자원, `waveCleared`, `battlesWon`, 퀘스트, 저장 상태를 변경하지 않는다.
- 리플레이에는 자원 보상, 약탈, 영웅 조각, 신규 해금, 추가 진행 보상이 일절 없다. UI는 시작 전과 GameOver에 `리플레이·보상 없음·상태 보존`을 명시해야 한다.

## 8. 조작, 화면, HUD와 피드백

- 모든 핵심 기능은 포인터/터치만으로 완료 가능해야 하고, 키보드만으로도 동등하게 완료 가능해야 한다.
- Title: `Space` 시작/이어하기, `S` 설정, `L` 언어. Town: 건물 선택, `B` 전투, `R` 연구, `H` 영웅, `Q` 퀘스트, `S` 설정, `Esc` 패널 닫기. Battle: `Esc`/Skip 즉시 결과. GameOver: `Space` Town, `R` 허용된 재도전, `Esc` Town.
- 하단 Town 액션은 전투·병영·연구·영웅·퀘스트·설정을 항상 찾을 수 있게 제공해야 한다. 패널은 제목, 상태, 비용/효과, 잠금 이유, 주 행동, 닫기를 갖춰야 한다.
- 상단 Town HUD는 네 자원과 실제 `+/s`, 저장 상한, 온기/연료, 방어력, 현재 웨이브/20을 표시해야 한다. 값이 바뀐 원인은 생산·소비·보상·약탈별로 짧게 피드백한다.
- 행동 성공은 시각+선택적 음향, 실패는 이유 텍스트+포커스 유지로 알려야 한다. disabled 버튼만으로 이유를 숨기지 않는다. 빠른 연속 입력은 한 번만 처리해야 한다.
- Battle HUD는 `웨이브 n/20`, 실제 아군·적 생존 수, 속도 `1×/2×/4×`, Skip을 표시한다. 화면 성능을 위해 유닛 스프라이트 수를 진영당 42개로 제한할 수 있으나 수치 HUD는 실제 총원을 표시해야 한다.
- 속도 변경은 이후 연출 시간만 바꾸고 공식 결과에는 영향을 주지 않는다. Skip은 모든 연출·예약 타이머를 정리하고 이미 커밋된 최종 상태와 GameOver 요약을 즉시 표시한다. Skip 자체가 상태·보상·진행을 mutation하는 횟수는 0회여야 한다.

## 9. 오디오와 비주얼

- 비주얼은 원본 중세 픽셀아트, 따뜻한 양피지·목재·석재 UI, 진영별 청색/적색 전투 식별, nearest-neighbour 렌더링을 유지해야 한다.
- 9건물, 5아군 병종, 4적 병종, 4영웅이 서로 구별되어야 한다. 웨이브 7 이후 기습병을 계산에만 넣고 화면에서 누락해서는 안 된다.
- Town/Battle 배경, 건설·타격·승리/패배 효과는 정보를 가리지 않아야 하며 reduced-motion에서는 필수 상태 전환만 남겨야 한다.
- 오디오는 반복 배경음과 UI 클릭, 건설, **실제 훈련 완료**, 타격, 승리, 패배 SFX를 제공해야 한다. enqueue를 훈련 완료로 재생해서는 안 된다.
- 설정은 전체/효과음/음악 3개 볼륨을 즉시 적용·저장해야 한다. 브라우저 autoplay 잠금 또는 오디오 누락은 플레이를 막지 않고 첫 사용자 입력 후 재개해야 한다.

## 10. 한·영 현지화와 접근성

- 첫 실행 기본 언어는 브라우저 언어와 무관하게 한국어다. 사용자가 한국어/English를 선택하면 즉시 전체 UI와 문서 언어를 바꾸고 별도 설정 저장에 영구 보존해야 한다.
- 모든 사용자 노출 문자열은 i18n 키를 사용하고 ko/en 키·placeholder parity를 유지해야 한다. 누락 문자열은 명시적 개발 경고와 안전한 fallback을 사용해야 한다.
- 숫자, 시간, 자원, 배율은 언어별 형식으로 표시하되 공식 값은 변하지 않아야 한다. 번역 때문에 버튼 텍스트가 잘리거나 패널이 가려져서는 안 된다.
- 핵심 플로우는 WCAG 2.2 AA의 적용 가능한 기준을 목표로 해야 한다: 논리적 Tab 순서, 보이는 포커스, Enter/Space 활성화, Esc 닫기, 포커스 트랩·복귀, 상태 이름/역할/값 제공.
- Canvas UI는 접근 가능한 DOM 제어/상태 미러 또는 동등한 의미 계층을 제공해야 한다. 자원 변화, 온기 경고, 전투 결과는 스크린리더가 과도한 반복 없이 알 수 있어야 한다.
- 텍스트/아이콘 대비는 4.5:1(큰 텍스트 3:1), 상태는 색상에만 의존하지 않고, 터치 대상은 최소 44×44 CSS px이어야 한다.
- 사용자 확대를 막아서는 안 되며 텍스트 200%에서도 핵심 기능을 잃지 않아야 한다. reduced-motion, 음소거 상태의 시각 피드백, 점멸 최소화를 제공해야 한다.

## 11. 반응형, 세로 모드, 터치, 성능

- 권위적 논리 해상도는 **960×540**이며 DPR을 제한한 캔버스를 viewport에 맞추고 종횡비와 픽셀 선명도를 유지해야 한다.
- 가로 화면은 기준 배치를 사용한다. 세로 화면은 단순 축소만 하지 말고 상단 자원/Hearth, 중앙 세계, 하단 행동을 재배치하며 패널을 safe-area 안의 스크롤 가능한 전체폭 sheet로 표시해야 한다.
- 최소 검증 viewport는 360×640 세로, 640×360 가로, 960×540, 1920×1080이다. 회전·resize 후 입력 좌표, 카메라, 패널 포커스와 진행 상태가 유지되어야 한다.
- 모든 포인터 상호작용은 mouse/touch/pointer에서 같아야 하고 hover를 필수 정보 전달 수단으로 사용해서는 안 된다. drag slider에는 탭과 키보드 대안을 제공한다.
- 일반 중급 모바일에서 Town 30fps 이상(목표 60fps), Battle 30fps 이상, 입력 피드백 100ms 이내를 목표로 한다. 동시 Battler 표현 수, 텍스트 texture DPR, tween/timer를 제한해야 한다.
- 최대 8시간 오프라인 정산은 UI를 장시간 멈추지 않아야 한다. 동일한 결정론을 유지하는 구간 병합 또는 분할 실행으로 목표 500ms, 상한 2초 안에 완료하고 진행/복구 상태를 표시해야 한다.

## 12. 저장, 오프라인, migration과 corruption

- 게임 진행은 `kingdom-rise:save` 단일 로컬 슬롯에 **save v7**으로 저장해야 한다. 설정은 진행 저장과 분리한다.
- v7은 resources, buildings/진행 타이머, army/trainingQueue, research, heroes/조각/active, quests, warmth, waveCleared, troopsTrained, battlesWon, onboarding/tutorial flags, lastSeenAt를 포함해야 한다.
- 자동 저장은 실제 플레이 경과 **15초마다** 수행한다. 업그레이드/훈련/연구 시작, 영웅 행동, 퀘스트 수령, 전투 진입·결과, 튜토리얼 완료/skip, 설정/화면 이탈, visibility/blur, 캠페인 완료에는 즉시 저장해야 한다.
- 저장 성공 전 UI가 영구 성공으로 오인하게 해서는 안 된다. quota/private mode/직렬화 실패를 catch하고 비차단 경고와 재시도 상태를 제공하되 현재 메모리 세션은 계속 플레이 가능해야 한다.
- 오프라인 경과는 `max(0, now-lastSeenAt)`에서 생산·Hearth 시뮬레이션에 최대 **28,800초(8시간)**만 인정한다. 기본 **50% 효율은 passive resource output에만** 적용하고 연구 `offlineEfficiency` 배율을 곱한다. 건설·연구·훈련의 절대 deadline, Hearth 연료 요구량, Warmth 증감 속도에는 50%를 적용하지 않는다.
- 건설·연구·훈련 timer는 wall-clock `now`까지 100% 진행하므로 8시간을 넘긴 부재에도 완료될 수 있다. 다만 8시간 밖 구간에는 생산 지급, 연료 소비, Warmth 증감이 없다.
- 인정 창은 `now-min(rawSeconds,28800)`부터 시작한다. 각 event boundary에서 due 건설을 canonical building order로 일괄 완료하고, 연구 완료, 훈련 완료 순으로 반영한 뒤 그 시점의 multiplier로 `생산×offlineEfficiency → Hearth 연료 전액 판정 → Warmth 갱신`을 실행한다. 새 Warmth는 다음 구간 생산부터 적용한다.
- 예: 연구 배율이 없고 Warmth가 최대인 3,600초 오프라인은 passive output 1,800초분을 지급하지만 Hearth는 3,600초분 연료를 요구한다. Warmth 0에서는 같은 구간 output이 live full-Warmth의 `0.5×0.25=12.5%`다.
- load 정산으로 완료된 훈련은 `troopsTrained`에 정확히 한 번 반영한다. 정산 성공 직후 새 `lastSeenAt`, 완료 marker, 결과 snapshot을 즉시 저장해 연속 reload의 재정산을 막는다.
- v1→v7은 additive migration으로 지원한다: v2 research, v3 heroes, v4 quests/counters, v5 warmth, v6 onboardingSeen, v7 tutorialDone. 누락 신규 필드는 안전한 기본값을 쓰고 기존 사용자는 온기 최대, onboarding/tutorial 완료로 이동한다.
- 로드 전에 schema와 모든 수치의 유한성·범위·ID·배열 형태를 검증하고 음수/NaN/미래 timestamp를 정규화해야 한다. 알 수 없는 ID는 격리하고 앱을 crash시켜서는 안 된다.
- JSON 손상, 구조 손상, 미지원 미래 버전은 원본을 복구용 backup 키로 보존하고 사용자에게 `새 게임 시작/백업 내보내기`를 알려야 한다. 조용히 반복 초기화해서는 안 된다.
- 시스템 시계가 뒤로 이동하면 오프라인 시간은 0으로 처리한다. 전투 보상과 즉시 저장은 idempotency guard로 중복 적용을 막아야 한다.

## 13. 기술 경계와 예외 처리

- 런타임은 TypeScript strict, Phaser 3.80 계열, Vite 5 계열, Node 22+ 빌드, Vitest를 기준으로 한다.
- `config/`는 수치·정적 roster, `systems/`는 Phaser/DOM 없는 순수 상태·공식, `scenes/`와 `ui/`는 입력·표현·오케스트레이션을 담당해야 한다. Scene이 경제·전투 공식을 복제해서는 안 된다.
- 결과에 영향을 주는 시간은 주입된 `now/delta`, 저장은 주입된 storage를 사용해야 한다. 순수 테스트에서 `window`, 실시간 timer, `Math.random()`에 의존해서는 안 된다.
- GameState는 단일 런타임 조정자이며 scene 전환 중 중복 tick/listener/timer를 남겨서는 안 된다. scene shutdown 시 모든 구독과 예약 작업을 해제해야 한다.
- 알 수 없는 패널/건물/기술/영웅/웨이브 입력은 no-op+개발 로그로 처리하고 사용자 상태를 변형해서는 안 된다.
- 에셋/폰트 로드 실패는 fallback 표시와 재시도 가능 상태로 처리한다. 핵심 데이터 config 또는 save 불변식 위반은 안전한 Title/Town 복구 경로를 제공해야 한다.
- 병력 부족, 자원 부족, queue full, prerequisite 미충족, max level, 연구 진행 중, 영웅 cap은 예상 가능한 도메인 거절이며 예외를 throw하지 않고 지역화 reason code를 반환해야 한다.

## 15. 출시 수용 기준

1. 새 게임이 한국어, 시작 자원 300/400/250/50, 청사 Lv.1, 최대 온기로 시작한다.
2. 1,000ms 생산을 반복한 결과와 같은 총 경과를 분할한 결과가 같고 수동 생산은 연구 적용 상한을 넘지 않는다.
3. 비용·시간·생산·청사 게이트 공식이 모든 레벨 0~20에서 config와 일치하고 원자적 지출이 검증된다.
4. 목재 충분/부족, 온기 0/35%/최대, 청사 여러 레벨에서 Hearth 소비·증감·생산 배율이 계약과 일치한다.
5. 라이브 1시간과 오프라인 1시간이 효율 차이 외 동일한 timer/Hearth 경계를 따라야 한다. 8시간 초과 부재는 **생산·연료·Warmth 정산만** 정확히 8시간 부재와 같고, 건설·연구·훈련 deadline은 전체 wall-clock 부재를 반영해 추가 완료될 수 있다.
6. 훈련 queue 6개, batch 1/20 경계, 순차 완료, 오프라인 완료, 누적 훈련 counter가 정확하다.
7. 5×5 상성 행렬과 적 역할 매핑이 계약과 일치하고 조합 변경이 예상 전투력을 바꾼다.
8. 15개 연구의 prerequisite/Hall gate/단일 slot/곱셈 배율과 4영웅의 역할·레벨·별·선택 배율이 실제 시스템에 연결된다.
9. 영입 전 받은 영웅 조각이 보존되고 9개 퀘스트가 순서대로 한 번만 수령된다. 왕실 후원은 영웅별 고정 비용을 원자 지출해 조각을 반복 지급하며 신규 저장에서 네 영웅 모두 5성까지 도달 가능해야 한다.
10. 전투는 오직 B/버튼/명시적 GameOver 선택으로 시작하며 대기·복귀·오프라인 중 자동 시작되지 않는다.
11. 웨이브 1, 7, 20의 구성·첫 보상과 경계 적 종류가 config 공식과 일치하며 네 적 종류 모두 시각화된다.
12. 고정 fixture에서 E/W, 승패, 병종별 사상/생존, 약탈, 방어 효과가 공식과 일치하고 반복 실행 결과가 byte-equivalent다.
13. 전투 결과는 연출 시작 전에 원자 저장되고, 저장 실패 시 rollback한다. 커밋 전/후 reload, skip 및 1×/2×/4× 각각이 동일한 최종 상태를 정확히 한 번 만들며 불리한 결과 회피·보상 중복·scene timer 잔존이 없어야 한다.
14. 웨이브 20 승리 후 wave 21 경로가 없고 Town 자유 플레이와 1~20 무상태·무보상 리플레이만 가능하다.
15. Title→Town→각 패널→Battle→GameOver→Town 전체 E2E가 mouse, touch, keyboard에서 완료된다.
16. 360×640 세로와 640×360 가로에서 핵심 HUD/행동이 safe-area 안에 있고 회전 후 상태·입력이 유지된다.
17. ko/en 키 parity, 긴 번역, 200% 텍스트, 키보드 포커스, 44px touch target, 색각·reduced-motion 검사가 통과한다.
18. 15초 autosave와 모든 즉시저장 지점, blur/reload, 저장 실패 경고가 fake storage와 실제 브라우저 통합 테스트에서 검증된다.
19. v1~v6 fixture가 상태 손실 없이 v7로 migrate되고, malformed JSON/shape/NaN/미래 버전이 crash 없이 backup·복구 안내로 이어진다.
20. Node 22에서 typecheck, 전체 Vitest, production build가 통과하고 일반 모바일 성능 목표를 프로파일로 입증한다.

## 16. 구현 현황과 목표 갭

### 16.1 현재 구현되어 목표의 기반이 되는 항목

- 전투는 Town preflight에서 군대·웨이브·연구·영웅·방어를 snapshot해 한 번 확정하고, 캠페인 사상자·보상/약탈·진행·receipt를 연출 전에 한 번 저장한다. temp/readback 실패 시 전체 상태를 rollback하며 미확인 receipt는 중복 요청과 reload 결과 재표시에 사용한다. Battle Skip/속도는 표현만 바꾸고 기습병도 spawn한다.
- 캠페인은 20에서 봉인된다. 완료 후 Town 선택기는 1~20만 허용하고 replay receipt는 현재 편성의 결과를 표시하되 자원·병력·진행·퀘스트·저장을 바꾸지 않는다.
- `SimulationEngine`이 라이브와 오프라인의 1,000ms 순서(해당 tick까지 도달한 건설 canonical batch→연구→훈련→생산→Hearth)를 공유한다. production/Hearth만 8시간 제한을 받고 deadline은 전체 wall-clock까지 진행하며 오프라인 훈련 counter와 즉시 reconcile 저장을 포함한다. 저장된 simulation cursor가 1초 미만 위상을 보존하고 전역 runtime coordinator가 모든 scene과 visibility/pagehide에서 tick/save 및 완료 피드백을 소유한다.
- v7 저장은 v1~v6 additive 기본값, 중첩 건설/연구/훈련 deadline·count의 엄격 검증, 청사 gate/진행 upgrade/온기 상한을 포함한 교차 불변식 정규화, 내부 수치/ID/배열 정규화, wave 20 clamp, temp write/readback 뒤 원자적인 primary commit, previous backup, 손상·미래 버전 quarantine/export 정보, 저장 실패 상태/재시도를 제공한다. transaction rollback은 load 정산을 실행하지 않는 hydration 경로로 exact snapshot을 복원한다.
- 영웅별 조각 지갑은 영입 전후 독립 보존되고 legacy recruited shards를 병합한다. 왕실 후원은 네 영웅의 정확한 고정 비용으로 영입 전후 반복 구매할 수 있으며 원자 지출·즉시 저장·실패 rollback을 사용한다.
- Town은 다음 canonical tick의 저장 상한과 Hearth 전액 결제 가능 여부까지 반영한 실제 gross/net 생산, Hearth 요구량, 저장 상한, 상세 온기/연료, wave/방어, 저장 상태를 표시한다. 실제 훈련 완료 SFX와 1회성 상세 오프라인 요약을 사용하고 Town 상태와 전체 battle result를 안정적인 semantic DOM region에도 제공한다.
- 전투 preflight/result는 E/W, 적 구성, 방어, 배율, 병종별 투입·사상·생존·상성 기여, 보상/약탈 또는 replay 무보상을 표시한다.
- 튜토리얼 청사 단계는 Lv.2 완료를 기다리고 마지막 단계는 실제 quest 열기/승리로 완료한다. 사용자 확대, 44px 최소 버튼, reduced-motion 경로, safe-area, Canvas 버튼 DOM mirror/live region을 추가했다. modal은 Tab/Esc focus trap과 호출 control 복귀를 사용하며, 세로 화면은 Town 상·하단을 viewport 가장자리에 재배치하고 전체폭 scroll sheet에 제목·비용·효과·진행·timer·거절 이유와 동등 action을 실시간 mirror한다.
- README와 config의 주기적 자동 침략·준비 countdown 표현을 제거하고 수동 20-wave 방어와 replay/save 동작을 문서화했다.

### 16.2 남은 출시 검증 갭

- preload의 개별 선택 에셋 실패 fallback/retry 화면과 일반 모바일 30fps, 오프라인 500ms 목표를 입증하는 실제 기기 프로파일은 아직 자동화되지 않았다.
- 저장·전투·orientation·touch·keyboard·접근성(360×640, 200% text 포함)의 브라우저 E2E suite는 이 패키지에 아직 없다. 이번 변경은 사용자 지시에 따라 새 테스트 파일/케이스를 추가하지 않고 기존 SPEC과 충돌한 shard/tutorial 및 tick-boundary assertion만 갱신했다.
